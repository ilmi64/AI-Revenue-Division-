# Trusted identity, approval issuance, clock and receiver-result boundary

Status: architecture requirement for production; companion SQLite reference remains offline synthetic only. This document does not claim that the current reference enforces these controls.

## Finding

The current reference's public methods accept caller-supplied identity fields, timestamps, approval documents/verifier objects, enqueue intents and sender-result labels. Matching those values to stored rows is useful transaction logic, but it does not authenticate the caller or prove that the caller is entitled to make the claim. The SQLite file must therefore never be exposed directly to model runtimes, agents, Paperclip, Ruflo, workers or user-facing tools.

## Required trust boundaries

1. **Authenticated principal.** The gateway obtains a signed, short-lived principal from a separate identity authority. It verifies issuer, signature, audience, company, agent, runtime/session, role, task assignment, issued-at/expiry, revocation and policy version. Company, agent, task, role and session values supplied in a request are claims to compare, never credentials. Model text, orchestration metadata and tool arguments are untrusted.
2. **Trusted time.** Expiry, freshness, revocation and replay decisions use a trusted clock injected by the control service. Do not accept a caller-provided `now` as authoritative. Reject invalid clock health, excessive skew and time rollback; fail closed. Record both trusted observation time and source metadata where required.
3. **Owner approval issuance.** The approval table is not an approval authority. Only a dedicated approval issuer may insert an approval after verifying the owner's asymmetric signature and exact action scope. Bind company, stream, principal, task, operation, resource/recipient, amount and currency, policy version, expiry, audience, nonce and one-time use. Agents and company runtimes cannot call approval issuance or write approval rows.
4. **Policy decision.** Before the transaction commits, a trusted policy authority evaluates current policy using authenticated identity, task assignment, immutable action digest, company/stream, resource, cost/amount/currency, recovery epoch, emergency stop and revocation state. The final transaction rechecks the policy version and relevant revocation/stop versions under a consistent transaction boundary. A model-generated allow decision is never authoritative.
5. **Immutable enqueue.** Only a trusted scheduler may enqueue after validating the signed task envelope and exact action intent. Bind a canonical intent digest, destination account, operation, recipient, amount/currency, idempotency key, company, stream and enqueue epoch. Agents cannot choose or rewrite company, approval ID, receiver or action identity. Database permissions/triggers must prevent mutation and unauthorized insertion.
6. **Dispatch authorization.** A narrow service API accepts an authenticated dispatch request, not raw identity claims. It resolves the trusted principal and action from authoritative stores, checks assignment and current policy, applies hard denies, and atomically consumes approval, advances dispatch state and appends audit in the same transaction. No model/runtime has direct database credentials.
7. **Receiver result.** Do not expose a method that accepts an unverified `accepted` / `rejected` string as proof of remote outcome. A receiver-evidence verifier must authenticate a signed response and bind issuer, audience, company, action ID, immutable intent digest, receiver account, idempotency key, operation, amount/currency, recovery epoch, outcome, timestamp and unique nonce. Durable replay receipt, state transition and audit append commit atomically. Missing, stale, mismatched, replayed or unverifiable evidence remains unknown/quarantined; it never becomes success.
8. **Recovery verifier custody.** Owner and assessor verifier implementations, trust roots, issuer registries, clocks and replay stores are configured by a separately administered recovery service. Callers cannot supply or replace verifier objects. Test doubles remain test-only and cannot be injected in production.
9. **Database and service isolation.** Each company has separate service identity, database/schema/keys and audit stream. Runtime agents receive no direct SQL access. Only narrow service identities receive stored-procedure/API access. Enforce row-level/company scoping, least privilege, secret separation, network segmentation and independent audit access. A shared database administrator remains a privileged threat requiring external controls and monitoring.
10. **Evidence and operations.** Preserve signed identity/approval/policy/receiver evidence references, canonical intent digest, trusted timestamps, recovery epoch and audit checkpoint. Monitor denied attempts, verifier/store/clock outages, replay, policy mismatch, stale epochs, unknown outcomes and privileged changes. Any control dependency unavailable or contradictory fails closed.

## Reference implementation disposition

The current SQLite reference is a transaction-ordering and state-machine teaching aid only. Its `company`, `agent`, `task`, `operation`, `resource`, `policy_version` and `now` arguments are not authenticated; its approval issuance method does not verify an owner signature; verifier objects are injected; enqueue is not a trusted scheduler; and its sender-result method accepts a label rather than verified receiver evidence. These are explicit production blockers, not small configuration gaps.

Do not connect this reference to real accounts, real customer data, payment systems, brokers, exchanges, wallets, signing services or network senders. Do not interpret local unit tests as proof of identity security or external-effect safety.

## Acceptance criteria

The companion acceptance matrix covers forged identity claims, cross-company impersonation, expired/revoked sessions, task reassignment, caller clock manipulation, unverified approval issuance, altered policy versions, forged enqueue destinations, verifier substitution, receiver evidence mismatch/replay/staleness, unknown outcomes, and control-service outages. All tests must run offline with synthetic fixtures before any production design review. Production additionally requires independent security review, cryptographic implementation review, database privilege review, restore/recovery rehearsal and receiver integration tests in a non-production sandbox.

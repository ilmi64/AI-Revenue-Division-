# Organisation Control Centre

This directory defines the organisation-level operating model. It is the coordination layer for all divisions, not a replacement for their specialist systems.

## Objectives
- Maintain one authoritative view of divisions, ownership, responsibilities, dependencies, and readiness.
- Coordinate shared priorities and cross-division support.
- Make risks, blockers, evidence, and approval gates visible.
- Support sustainable funding through the AI Revenue Division while protecting the organisation from dependence on any single revenue source.

## Core records
- `division-registry.json`: division mandates, status, dependencies, and approval boundaries.
- `readiness-register.json`: evidence-based readiness checks and current status.

## Operating cycle
1. Each division reports deliverables, evidence, blockers, risks, and next actions.
2. The executive layer reviews cross-division dependencies and prioritises work.
3. Risk and advisory functions can flag or recommend stopping unsafe work; they cannot authorise financial or operational execution.
4. Readiness changes only when evidence is recorded and reviewed.
5. Decisions requiring owner approval remain pending until explicitly approved.

## Status vocabulary
- `planned`: defined but not yet established.
- `building`: active development.
- `testing`: implementation exists and is undergoing verification.
- `standby`: tested for its defined scope, with dependencies and limitations documented.
- `operational`: approved for its stated non-sensitive operating scope.
- `blocked`: cannot progress until a named blocker is resolved.
- `deferred`: intentionally postponed.

A division is never marked operational merely because a document, repository, or prototype exists.

## Approval boundaries
This framework does not authorise spending, borrowing, banking activity, trades, wallet access, signing, external client commitments, public launches, production deployments, merges, or permission changes. Those actions require the applicable explicit owner approval and any required independent review.

## Reporting minimum
Every division update should include: current status, completed work with links/evidence, tests and results, open risks, dependencies, owner actions needed, and next measurable deliverable.

## Current implementation scope
This is a documentation-and-data foundation on a feature branch. It is not yet an integrated dashboard, automated control plane, or proof that any division is launch-ready.

## Local validation

From the repository root, run:

```sh
python organization/tools/validate_readiness.py
python -m unittest discover -s organization/tests -v
```

The validator checks registry references, status vocabulary, assessment structure,
and evidence gates. It deliberately blocks `standby` or `operational` claims
unless every required check has an explicit `passed` result with evidence and
there are no open gaps. Missing division assessments are reported as warnings;
they are not silently treated as ready. This is a data-integrity check, not a
substitute for real operational testing or owner approval.

## Cross-division dependency view

The dependency map in `dependency-map.json` records required and supporting
capabilities between divisions. Run:

```sh
python organization/tools/build_dependency_report.py
```

A required dependency is satisfied only when the provider's verified readiness
status is `standby` or `operational`. Supporting gaps are visible but do not
independently block the dependent division. The report never changes division
status or authorises work. The dependency report is also generated by the
pull-request workflow.

## Consolidated executive dashboard

Generate the combined organisation view with:

```sh
python organization/tools/build_organisation_dashboard.py
```

The JSON report combines the division scorecard, verified readiness, dependency
blockers, AI Revenue pipeline and ledger snapshot, recorded readiness risks,
outstanding decision prompts, and reserved owner approvals. It is read-only:
it does not promote readiness, authorise actions, connect accounts, or verify
bank balances. Missing assessments remain `unassessed`; they are never treated
as operational. The dashboard is also generated by the pull-request workflow.

## Division operating framework

The proposed operating design for all nine divisions is in
`operating-framework.json`. It defines each division's purpose,
responsibilities, deliverables, reporting cadence, handoffs, measurable
acceptance criteria, owner-assignment state, and approval boundary.

Validate it with:

```sh
python organization/tools/validate_operating_framework.py
```

This is a designed framework pending owner confirmation, not proof that roles
are staffed or cadences are already being met. Deferred divisions remain
deferred; owner assignments that need confirmation are labelled explicitly.
The validator checks full registry coverage, required sections and handoff
references. The consolidated dashboard includes its validation summary, and
the pull-request workflow runs the validator and regression tests.


## Division work queue

The proposed organisation-wide queue is in `work-queue.json`. It seeds measurable work across all nine divisions with task IDs, priority, dependencies, required evidence, acceptance criteria, ownership state, execution state and approval gates.

Validate it with:

```sh
python organization/tools/validate_work_queue.py
```

The queue is a planning record, not proof that tasks have been assigned or started. All 18 initial tasks remain proposed and unassigned pending owner confirmation. Dependencies are reported as blockers until their prerequisite tasks have evidence-backed completion. A task cannot be marked completed without completion evidence and a timestamp; work cannot be marked in progress without an assigned owner. The dashboard includes the read-only queue summary, and CI checks its schema, dependency references, cycle safety and state transitions.


## Division execution and evidence reporting

`execution-log.json` is the append-only event record for task starts, progress, blockers, pauses, resumptions and completion evidence. Each event identifies the task, actor, timestamp with timezone, summary and evidence references.

Validate the log with:

```sh
python organization/tools/validate_execution_log.py
```

The validator rejects unknown task IDs, duplicate event IDs, missing actors or timestamps, timezone-free timestamps, invalid event transitions, unassigned-owner starts/completions and completion events without evidence. The dashboard reports events by division and derives task state from the event stream; it does not mutate the work queue or treat a report as independently verified fact. The log starts empty, so it does not imply that work is underway. CI runs this validator and the full test suite.


## Incident response and corrective-action tracking

`incident-register.json` is the evidence-backed incident and recovery record. It starts empty; absence of records is not evidence that no incidents occurred elsewhere. Each incident must identify its affected division, severity, detection evidence, containment recommendation and valid links to risks, tasks and owner decisions. Corrective actions remain proposed until ownership is confirmed; assignment, progress and completion are not inferred. Completed actions require completion evidence.

An incident cannot be recorded as closed until post-incident review evidence exists, every corrective action is completed, and a linked owner decision is approved with outcome evidence. A deferred action linked to a pending owner decision does not satisfy closure. Critical/high incident records are surfaced in the dashboard and follow the existing Risk stop-only advisory route; this does not execute containment, rollback, notification or approval.

Validate with:

```sh
python organization/tools/validate_incident_register.py
```

The dashboard reports the register and data-quality errors read-only. CI runs the validator and incident lifecycle tests.


## Technical backup, restore, rollback and restart recovery

The proposed recovery procedures are recorded in organization/recovery-plan.json. They define evidence required for backup integrity, isolated restore, rollback validation and restart health checks. Their production state remains not tested until the relevant service, data owner, approved backup location, recovery objectives, authorization and independent evidence are recorded.

Run the safe local drill with:

```sh
python organization/tools/run_recovery_drill.py
```

The drill creates disposable files in a temporary directory, verifies SHA-256 backup integrity, restores a deliberately altered fixture, rolls a fixture back to its pre-change state and checks a synthetic health marker. CI runs this drill and its regression tests.

A passing result proves only that the temporary-fixture drill harness works. It does not prove production backup coverage, real application/database restore, service restart, recovery time objective (RTO), recovery point objective (RPO), or launch readiness. No production data, credentials, service commands, wallets or external systems are touched. Production recovery or rollback requires explicit owner approval and a separately validated target-specific runbook.
